[![CI](https://github.com/nicoavril1231-dev/churn-prediction/actions/workflows/ci.yml/badge.svg)](https://github.com/nicoavril1231-dev/churn-prediction/actions/workflows/ci.yml)

Production-grade machine learning pipeline that predicts customer churn for a
telecom operator — from raw data to a containerized REST API, with MLflow
experiment tracking, pytest coverage, and a CI workflow that smoke-tests the
Docker image.

> **🚀 Live API**: [`churn-prediction-q6la.onrender.com/docs`](https://churn-prediction-q6la.onrender.com/docs) — Swagger UI, real predictions on a real model. Free tier sleeps after 15 min idle (cold start ~30s on first hit).

> **Why this repo?** Most public ML notebooks stop at "I trained a model on
> Kaggle." This one shows the full delivery loop a Data Scientist or ML
> Engineer is expected to own: clean code, tests, calibrated probabilities,
> a deployable artifact, reproducible builds.

## Headline results

| Model | ROC-AUC | F1 | Recall | CV ROC-AUC |
|---|---|---|---|---|
| Logistic Regression (balanced) | **0.835** | 0.607 | **0.797** | 0.846 ± 0.005 |
| XGBoost | 0.821 | 0.608 | 0.735 | 0.840 ± 0.006 |
| LightGBM | 0.823 | 0.608 | 0.714 | 0.832 ± 0.005 |

Dataset: [IBM Telco Customer Churn](https://www.ibm.com/communities/analytics/watson-analytics-blog/predictive-insights-in-the-telco-customer-churn-data-set/) — 7,032 customers × 21 features, 26.5% positive rate.

**Why does Logistic Regression win?** Telco is small (n ≈ 7k), heavily
categorical, and class boundaries are largely linear. Boosting overfits
slightly here. Discussion in [`notebooks/02-modeling.ipynb`](notebooks/02-modeling.ipynb).

## Quickstart

```bash
# 1. Setup (requires Python 3.11 and uv)
git clone https://github.com/nicoavril1231-dev/churn-prediction.git
cd churn-prediction
uv venv && uv pip install -e ".[dev]"

# 2. Download data + train
uv run python -m churn.data
uv run python -m churn.train

# 3. Run tests
uv run pytest                  # 19 tests, ~5s

# 4. Start the API
uv run uvicorn api.main:app --reload
# → http://localhost:8000/docs

# 5. (Optional) MLflow UI to compare runs
uv run mlflow ui --port 5000
```

Or with `make install && make train && make api`.

## Engineering choices worth noting

- **`uv` for dependency management** — 10× faster than pip, lockfile-driven,
  works in CI without virtualenv juggling.
- **`OneHotEncoder(handle_unknown='ignore')`** — unseen categories at
  inference don't crash; they encode to all zeros (regression-aware fallback).
- **`scale_pos_weight=2.77`** for XGBoost — ratio of negative/positive in
  Telco (26.5% churn → 73.5/26.5 ≈ 2.77). Equivalent to `class_weight='balanced'`
  for the linear model.
- **Cost-aware threshold optimisation** — default 0.5 is rarely optimal in
  business contexts. Notebook 02 walks through a threshold sweep with
  asymmetric FN/FP costs ($1000 vs $50) and shows the cost-minimum is well
  below 0.5.
- **Calibrated probabilities** — when downstream uses *probabilities* (not
  just labels), wrap the estimator in `CalibratedClassifierCV(method='sigmoid')`.
  Demonstrated in notebook 02.
- **Multi-stage Docker** — builder trains the model, runtime is slim
  (production deps only, non-root user, healthcheck).
- **Pydantic 2 strict schemas** — typed enums for every categorical, range
  constraints for numerics, `extra="forbid"` to reject unknown fields.
- **No mocks for the API tests** — tests exercise the real model, real
  Pydantic validation, real FastAPI dispatch. CI trains a model first.

## Deploy

A [`render.yaml`](render.yaml) Blueprint is included so the service can be
deployed in three clicks:

1. Sign in at [render.com](https://render.com) with GitHub.
2. **New** → **Blueprint** → select `nicoavril1231-dev/churn-prediction`.
3. **Apply** — Render reads the yaml, builds the Docker image, runs the
   healthcheck on `/health`, and exposes the service at
   `https://churn-prediction-<id>.onrender.com`.

The free plan sleeps after 15 minutes of inactivity (cold start ~30s on
first hit). For always-on serving, switch the `plan` field to `starter`.
